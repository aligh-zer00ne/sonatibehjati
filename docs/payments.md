# اتصال درگاه سامان

پیاده‌سازی بر اساس مجموعهٔ Postman سال ۱۴۰۵، نمونه‌کدهای تحویلی و مستند فنی رسمی نسخهٔ ۳٫۶ همراه آن‌ها انجام شده است. شمارهٔ ترمینال در فایل خصوصی API ذخیره می‌شود؛ کلید، توکن بانک و اطلاعات کارت در سورس و خروجی عمومی قرار نمی‌گیرند.

## تست درگاه بدون پیامک

**این بخش مربوط به دورهٔ قبلی است.** درخواست جدید مالک، خروج از تست و فعال‌سازی پیامک واقعی است. برای انتشار، `npm run production:configure -- --body-id=559650 --terminal-id=15855486` و سپس `bash deploy/update-production.sh` اجرا شود؛ دستورهای کامل در [انتشار واقعی](production.md) هستند. فرمان‌های تست زیر دوباره اجرا نشوند مگر برای یک آزمون جدیدِ صریحاً درخواست‌شده.

طبق درخواست قبلی، تست از **همین فروشگاه و مسیر معمول خرید** انجام می‌شود: شماره موبایل، کد ثابت **۱۲۳۴۵۶**، سبد خرید، نشانی، ثبت سفارش و درگاه واقعی سامان. نیازی به ملی‌پیامک یا نسخهٔ جدا نیست. این پرداخت به سفارش واقعی متصل است و پرداخت موفق خودکار برگشت داده نمی‌شود.

بعد از رسیدن کامیت‌ها به `origin/dev`، روی سرور با کاربر پروژه اجرا کنید:

```bash
sudo -iu sonatibehjati
cd /var/www/sonatibehjati
git switch dev
git pull --ff-only origin dev && npm run payments:checkout-test -- --terminal-id=15855486 && bash deploy/update-production.sh
exit
```

این فرمان تنظیمات خصوصی API و فروشگاه را هماهنگ می‌کند: `NODE_ENV=production`، `CUSTOMER_AUTH_ENABLED=true`، `CHECKOUT_PAYMENT_TEST_ENABLED=true`، `ADMIN_PAYMENT_TEST_ENABLED=false` و `PAYMENT_PROVIDER=sep`. ارسال پیامک کاملاً کنار گذاشته می‌شود؛ کلیدهای مستقل احراز هویت، اطلاعات اتصال دیتابیس و کلید پیامک موجود حفظ می‌شوند. تنظیمات متعارض `.env.local` یا `.env.production.local` پیش از هر تغییری گزارش می‌شوند. این فرمان مخصوص سرور است؛ در محیط توسعهٔ محلی اجرا نشود.

برای باز شدن ورود مشتری، یک بار کانفیگ فعلیِ پیش‌نمایش را با کانفیگ همین فروشگاه جایگزین کنید:

```bash
sudo cp -a /etc/nginx/sites-available/sonatibehjati.conf /etc/nginx/sites-available/sonatibehjati.conf.before-checkout-test
sudo install -m 644 /var/www/sonatibehjati/deploy/nginx/payment-live.conf /etc/nginx/sites-available/sonatibehjati.conf
sudo nginx -t && sudo systemctl reload nginx
```

سپس از `https://sonatibehjati.ir/login` با شمارهٔ خود و کد `123456` (اعداد فارسی هم پذیرفته می‌شوند) وارد شوید و یک سفارش کم‌مبلغ ثبت کنید. صفحهٔ ورود آزمایشی بودن را نشان می‌دهد؛ کد فقط پس از ثبت درخواست ورود، با محدودیت تلاش، انقضا و مصرف یک‌بارهٔ همان درخواست معتبر است. نشست‌ها و کوکی‌ها همچنان تنظیمات production را دارند.

تا وقتی این حالت روشن است، دانستن شمارهٔ هر مشتری برای ورود به حساب او کافی است. پس از تست، با آماده شدن پیامک واقعی، `npm run payments:configure -- --activate` و سپس `bash deploy/update-production.sh` را اجرا کنید؛ حالت تست خاموش و کد واقعی ۵ رقمی می‌شود. برای بستن موقت ورود پیش از آماده شدن پیامک، `payments:review` و دیپلوی معمول ورود مشتری را غیرفعال می‌کند. در حالت قدیمیِ تست مدیریتی، رفتار مبلغ و برگشت وجه متفاوت است؛ [راهنمای آن](gateway-review-deploy.md) فقط برای همان گزینه است.

## رفع خطای «درخواست مجاز نیست» در ورود

بررسی Origin در `/api/auth` بر اساس `STOREFRONT_ORIGIN` تنظیم‌شده انجام می‌شود؛ آدرس داخلی Next.js پشت Nginx معیار دامنهٔ عمومی نیست. درخواست از دامنهٔ دیگر همچنان رد می‌شود. برای دریافت اصلاح، همان به‌روزرسانی معمول کافی است:

```bash
cd /var/www/sonatibehjati
git pull --ff-only origin dev && bash deploy/update-production.sh
```

اگر حالت `payments:checkout-test` و کانفیگ `payment-live.conf` قبلاً فعال شده‌اند، نیازی به تغییر دوبارهٔ env یا Nginx نیست؛ ورود با کد **۱۲۳۴۵۶** حفظ می‌شود.

## وضعیت تأیید واقعی درگاه

در آزمون دریافت توکن از سیستم توسعه، سامان HTTP 200 با `status=-1` و `errorCode=8` و پیام «آدرس سرور پذیرنده نامعتبر است» برگرداند. در مستند تحویلی این کد `MerchantIpAddressIsInvalid` است. این نتیجه وضعیت مبدأ همین درخواست را نشان می‌دهد؛ پذیرش IP سرور سایت باید از همان سرور بررسی شود. هیچ مبلغی در آن آزمون محلی پرداخت نشد. پس از دیپلوی و اصلاح ورود، کاربر در ۱۶ اکتبر ۲۰۲۶ تأیید کرد درگاه واقعی روی سایت کار می‌کند؛ نتیجهٔ خطای ۸ بالا مربوط به مبدأ سیستم توسعه بود.

## رفتار پرداخت

- مبلغ ذخیره‌شدهٔ سفارش مبناست؛ تبدیل تومان به ریال فقط سمت API انجام می‌شود. مبلغ مرورگر پذیرفته نمی‌شود.
- شروع پرداخت به صاحب سفارش محدود است. درخواست هم‌زمان، کلیک تکراری، بازگشت تکراری و قطع ارتباط باعث ثبت دوبارهٔ پرداخت موفق نمی‌شوند.
- مرورگر با فرم POST و هدر ارجاع شامل فقط مبدأ سایت به سامان می‌رود. آدرس بازگشت برای هر تلاش جدا و دارای شناسه و کلید تصادفی است: `https://sonatibehjati.ir/payment/sep/callback/<id>/<key>`.
- بازگشت بانک به ورود کاربر وابسته نیست. صفحهٔ نتیجه بدون کوکی ورود هم کار می‌کند و اطلاعات نشانی، موبایل، کارت یا توکن را نشان نمی‌دهد.
- فقط تأیید مستقیم بانک با تطبیق رسید، ترمینال و مبلغ، `paidAt` سفارش را ثبت و وضعیت سفارش را «در حال آماده‌سازی» می‌کند. پیام موفق در URL یا فرم بازگشت برای این کار کافی نیست. پاسخ تکراری بانک فقط با جزئیات معتبر بازیابی می‌شود.
- لغو، رد پرداخت، انقضای توکن و شکست دریافت توکن جدا نمایش داده می‌شوند و سفارش محفوظ می‌ماند. نتیجهٔ نامعلوم یا قطع ارتباط «در انتظار تأیید» است؛ پرداخت مجدد تا روشن شدن نتیجه بسته می‌ماند.
- کارگر داخل API هر ۳۰ ثانیه بررسی‌های باقی‌مانده را ادامه می‌دهد و پس از restart نیز از وضعیت ذخیره‌شده استفاده می‌کند. نیازی به cron یا سرویس جدید نیست. فاصلهٔ بررسی تراکنش‌های قدیمی بیشتر می‌شود؛ پس از ادامهٔ ابهام، وضعیت برای بررسی پشتیبانی نگه داشته می‌شود.
- مبلغ نامعتبر، پرداخت اضافهٔ همان سفارش یا پرداخت دیرهنگام سفارش لغوشده، پس از تأیید مالکیت رسید به درخواست برگشت وجه منتهی می‌شوند. رسید متعلق به سفارش دیگر یا ترمینال متفاوت خودکار برگشت نمی‌خورد. «وجه برگشت داده شد» فقط پس از پاسخ تأیید بانک نمایش داده می‌شود.
- در پنل، تاریخچهٔ پرداخت و شمارهٔ پیگیری نمایش داده می‌شود و مدیر دارای دسترسی سفارش‌ها می‌تواند بررسی بانک را تکرار کند. سفارش پرداخت‌نشده در حالت درگاه فعال نمی‌تواند دستی آماده یا ارسال‌شده شود. درآمد از پرداخت‌های تأییدشده محاسبه می‌شود.
- لغو اداری سفارشی که قبلاً با موفقیت پرداخت شده، به‌تنهایی وجه را پس نمی‌دهد. بازپرداخت چنین سفارشی باید با پشتیبانی و روش مورد پذیرش سامان انجام شود؛ API برگشت دارای محدودیت زمانی است و جایگزین بازپرداخت‌های بعدی نیست.
- اگر خریدار پس از بانک به سایت برنگردد و رسیدی نرسد، سایت نمی‌تواند موفقیت را اعلام کند. چنین موردی باید با رسید بانک پیگیری شود؛ پایان مهلت توکن به معنای تأیید برگشت وجه نیست.

## دیپلوی

برای نصب کد با خرید عمومیِ بسته، همان `deploy/update-production.sh` کافی است؛ migrationها خودکار اجرا می‌شوند. تنظیمات خصوصی، دیتابیس و فایل‌های آپلود حفظ می‌شوند. تنظیم Nginx فعلی `payment-review.conf` را نگه دارید. نیازی به seed، ساخت مدیر یا نصب سرویس جدا نیست.

فعال‌سازی عمومی یک مرحلهٔ جداست و به پیامک واقعی، تنظیمات production و پذیرش درخواست توسط سامان نیاز دارد. پس از آماده شدن پیامک، روی سرور و با کاربر پروژه:

```bash
sudo -iu sonatibehjati
cd /var/www/sonatibehjati
git switch dev
git pull --ff-only origin dev
# پیامک واقعی و کلیدهای احراز هویت باید از قبل در apps/api/.env تنظیم باشند.
# شناسهٔ ترمینال را فقط در env خصوصی ذخیره کنید.
npm run payments:configure -- --activate
bash deploy/update-production.sh
exit
```

ابزار تنظیمات قبل از نوشتن فایل، پیامک واقعی و کلیدهای مستقل را بررسی می‌کند؛ بدون پیامک اجرا متوقف می‌شود. شمارهٔ ترمینال باید در `SEP_TERMINAL_ID` خصوصی موجود باشد؛ در صورت نبودن، با گزینهٔ `--terminal-id=...` به همین ابزار بدهید. از گزینهٔ `--activate` در سیستم توسعه استفاده نکنید. بدون انتخاب هیچ‌یک از حالت‌های `--activate`، `--checkout-test` یا `--review`، ابزار فقط تنظیمات ترمینال را ذخیره و پرداخت و ورود آزمایشی را غیرفعال می‌کند.

بعد از بالا آمدن API production و فروشگاه، فقط کانفیگ همین پروژه را فعال کنید:

```bash
sudo cp -a /etc/nginx/sites-available/sonatibehjati.conf /etc/nginx/sites-available/sonatibehjati.conf.before-live-payment
sudo install -m 644 /var/www/sonatibehjati/deploy/nginx/payment-live.conf /etc/nginx/sites-available/sonatibehjati.conf
sudo nginx -t
# فقط پس از موفقیت و نبود هشدار دامنهٔ تکراری:
sudo systemctl reload nginx
```

کانفیگ جدید از همان دامنه‌ها، پورت‌های ۳۱۰۰/۴۱۰۰ و گواهی فعلی استفاده می‌کند و ورود واقعی مشتری را باز می‌کند. مسیر callback باید از اینترنت بدون Basic Auth در دسترس باشد. بعد از فعال‌سازی، ورود با پیامک واقعی و یک خرید کم‌مبلغ از دامنهٔ اصلی را بررسی کنید: توکن، نمایش بانک، بازگشت، رسید، `paidAt` سفارش و وضعیت پنل. خطای ۸ از سرور اصلی نیازمند پیگیری تنظیم مبدأ پذیرنده نزد سامان است. آزمون‌های محلی جایگزین این آزمون واقعی نیستند.

## آزمون‌های محلی

پس از آماده بودن دیتابیس محلی و build پروژه:

```bash
npm run verify:payments
npm run verify:payments-ui
npm run verify:checkout-payment-test
npm run verify:payment-deploy
```

این دستورها فقط در محیط توسعه اجرا شوند. بانک شبیه‌سازی‌شدهٔ localhost، ترمینال ساختگی و سفارش‌های موقت به کار می‌روند. مرورگر درخواست به صفحهٔ سامان را قطع و پاسخ بانک آزمایشی جایگزین می‌کند؛ وجه واقعی پرداخت نمی‌شود. رکوردهای TEST از کارگر و درآمد LIVE جدا هستند. داده‌های موقت پس از آزمون پاک می‌شوند.

## دریافت وجه با لینک مستقل

در پنل «دریافت و پرداخت ← لینک‌های پرداخت» می‌توان لینک ماندهٔ حساب دستی مشتری یا مبلغ دلخواه بدون ساخت سفارش ایجاد کرد. لینک فقط کپی/اشتراک‌گذاری می‌شود؛ پیامک نمی‌فرستد و پرداخت‌کننده به ورود نیاز ندارد. ثبت دریافت منوط به همان تأیید مستقیم سامان است. دریافت مشتری وارد دفتر حساب و تسویهٔ FIFO می‌شود؛ دریافت بدون مشتری جدا در گزارش می‌آید. نتیجهٔ نامعلوم اجازهٔ پرداخت مجدد نمی‌دهد و مدیر از جزئیات لینک می‌تواند استعلام بانک را تکرار کند.

مسیر عمومی `/pay/<id>/<key>` با Nginx فعلی به Next.js می‌رسد؛ مسیر callback همان `/payment/sep/callback/...` است. هدرهای noindex/no-referrer و جلوگیری از cache روی مسیر جدید اعمال شده‌اند. تنظیم ترمینال و مبدأ بازگشت فعلی کافی است. این قابلیت migration افزایشی دارد که `deploy/update-production.sh` اجرا می‌کند؛ دستور seed/reset اجرا نکنید.

پس از انتشار، ابتدا ساخت/کپی لینک، مبلغ و انقضا را در دامنهٔ اصلی بررسی کنید. در تست بانکی کوچک با رضایت پرداخت‌کننده، رسید تأییدشده، کاهش مانده و گزارش را بررسی کنید؛ تست‌های محلی پروژه از بانک شبیه‌سازی‌شده استفاده می‌کنند و جای پرداخت واقعی روی دامنه را نمی‌گیرند.
