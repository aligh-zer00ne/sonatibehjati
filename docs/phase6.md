# فاز ۶ — Checkout

سبد مهمان به `/checkout` وصل است. ورود فقط هنگام ادامهٔ سفارش لازم می‌شود و بعد از OTP کاربر به Checkout بازمی‌گردد. کاربر نشانی را ایجاد، ویرایش، انتخاب یا حذف می‌کند؛ سپس هزینهٔ ارسال، تخفیف و خلاصهٔ سرور را می‌بیند. تأیید ثبت سفارش به `/checkout/order/[id]` می‌رود و وضعیت «در انتظار پرداخت» را نشان می‌دهد. درگاه یا پرداخت موفق ساختگی وجود ندارد. پروفایل و فهرست کامل سفارش‌ها در فاز ۷ هستند.

## احراز هویت

طبق تصمیم کاربر، access در حافظهٔ ماژول مرورگر نگهداری و با `Authorization: Bearer` ارسال می‌شود؛ API access-cookie را قبول نمی‌کند. refresh در کوکی HttpOnly می‌ماند. SSR مسیر خصوصی وجود refresh-cookie را برای هدایت مهمان بررسی می‌کند؛ اطلاعات و عملیات خصوصی فقط پس از اعتبارسنجی امضا و نشست فعال در API قابل دریافت‌اند. access پس از reload و نزدیک انقضا بازیابی می‌شود، خطای UNAUTHENTICATED یک بار با refresh معتبر دوباره تلاش می‌شود و پایان قطعی نشست به AuthProvider اعلام می‌شود. Web Locks و BroadcastChannel تمدید و خروج میان تب‌ها را هماهنگ می‌کنند. اسرار و نشست مدیر مستقل‌اند.

## قراردادهای API

Schema و Codegen منبع قرارداد هستند. queryهای `myAddresses`، `checkoutQuote`، `orderReceipt`، `orderByRequestId` و `reverseLocation` و mutationهای `saveAddress`، `deleteAddress` و `createOrder` اضافه شدند. پراکسی Next فقط documentهای تولیدشده و ورودی‌های مشترک Zod را قبول می‌کند. خروجی‌ها بدون cache هستند؛ توکن refresh یا خطای داخلی API به JSON مرورگر راه ندارد. سقف بدنهٔ پراکسی ۳۲ کیلوبایت است.

هر نشانی فقط برای مالک قابل خواندن و تغییر است. عنوان، نام و شمارهٔ گیرنده، استان، شهر، نشانی کامل، کد پستی ده‌رقمی، مختصات اختیاری و پیش‌فرض ثبت می‌شوند. ارقام فارسی پذیرفته می‌شوند؛ مختصات باید با هم و در محدودهٔ معتبر باشند. سقف بیست نشانی برای هر کاربر اعمال می‌شود. قفل سطر User تغییر پیش‌فرض و ساخت سفارش را سری می‌کند. نشانی استفاده‌شده در سفارش قابل حذف نیست؛ ویرایش آن snapshot سفارش قبلی را تغییر نمی‌دهد.

## نقشه و نشانی پیشنهادی

`AddressMapService` آداپتور نقشه و geolocation در فروشگاه است و پیاده‌سازی Leaflet 1.9.4 از tileهای OpenStreetMap استفاده می‌کند. کلیک روی نقشه، جابه‌جایی marker، موقعیت فعلی، رد دسترسی، timeout و نبود پشتیبانی مرورگر مدیریت می‌شوند. موقعیت اختیاری است و نوشتن دستی نشانی همیشه ممکن است. کنترل‌های نقشه با صفحه‌کلید قابل استفاده‌اند. Leaflet به‌صورت پویا بارگذاری می‌شود؛ CSS واردشده صرفاً CSS خود کتابخانه است و استایل‌های برنامه در classNameهای Tailwind و primitiveهای shadcn هستند. فایل‌های marker از بستهٔ Leaflet مشتق شده‌اند.

Reverse geocoding پشت `GeocodingService` در API است. Nominatim فقط با کلیک صریح «دریافت نشانی پیشنهادی» فراخوانی می‌شود؛ هنگام جابه‌جایی marker درخواست خودکار ندارد. نتیجه برای تکمیل و بررسی پلاک/واحد پیشنهاد می‌شود و نشانی قطعی تلقی نمی‌شود. آداپتور دارای User-Agent معرف برنامه، timeout پنج ثانیه، صف سری با فاصلهٔ حداقل ۱٫۱ ثانیه، cache یک‌روزه با سقف هزار موقعیت و سقف صف پنج درخواست است. محدودیت هر کاربر شش درخواست در دقیقه است. این صف و cache برای یک instance API هستند؛ برای چند instance باید queue/cache مشترک یا provider دیگری استفاده شود.

انتساب OpenStreetMap روی نقشه و انتساب Nominatim کنار نشانی پیشنهادی نمایش داده می‌شوند. قراردادها از [مستندات Leaflet](https://leafletjs.com/reference.html)، [سیاست tileهای OpenStreetMap](https://operations.osmfoundation.org/policies/tiles/) و [سیاست Nominatim](https://operations.osmfoundation.org/policies/nominatim/) پیروی می‌کنند. تست‌ها tile و پاسخ reverse را کنترل می‌کنند؛ دسترس‌پذیری زندهٔ سرویس خارجی تضمین یا ادعا نشده است.

## قیمت، ارسال و تخفیف

سرور محصولات فعال را از دیتابیس می‌خواند؛ مبلغ یا قیمت فرستاده‌شده از مرورگر مبنای محاسبه نیست. سبد باید غیرخالی، بدون محصول تکراری، حداکثر دویست ردیف و هر ردیف یک تا نودونه عدد باشد. قیمت‌ها و جمع‌ها تومان صحیح با سقف Int هستند.

`ShippingService` فعلاً نسخهٔ `FixedShippingService` دارد و هزینه از `SHIPPING_COST` می‌آید؛ نمونهٔ توسعه ۶۰٬۰۰۰ تومان است. هزینه تنها در سرور محاسبه می‌شود و provider آینده قابل جایگزینی است.

کد تخفیف در سرور بر اساس فعال‌بودن، شروع/پایان، حداقل خرید، نوع درصدی/ثابت، سقف تخفیف و سقف مصرف اعتبارسنجی می‌شود. درصد به پایین گرد می‌شود؛ تخفیف از subtotal بیشتر نمی‌شود. quote مصرف ایجاد نمی‌کند. ثبت سفارش، مصرف تخفیف و snapshot در یک transaction انجام می‌شوند. قفل محصولات با ترتیب ثابت و قفل کد تخفیف از محاسبهٔ ناسازگار و مصرف هم‌زمان بیشتر از سقف جلوگیری می‌کنند.

## ثبت سفارش و بازیابی

سرور هنگام create دوباره قیمت، ارسال و تخفیف را محاسبه می‌کند. `expectedTotal` فقط برای تشخیص تغییر مبلغ نسبت به خلاصهٔ دیده‌شده است؛ مبلغ مرجع از سرور می‌آید. تغییر مبلغ با `PRICE_CHANGED` ثبت را متوقف می‌کند تا کاربر خلاصهٔ تازه را ببیند. محصول ناموجود و تخفیف نامعتبر هم ثبت نمی‌شوند.

نشانی و عنوان/وزن/قیمت محصولات snapshot می‌شوند. `clientRequestId` یکتا برای هر کاربر و `requestHash` در migration `202610020002_checkout` اضافه شدند. درخواست هم‌زمان یا دوباره با همان شناسه و بدنه همان سفارش را برمی‌گرداند؛ تغییر بدنه برای شناسهٔ مصرف‌شده `REQUEST_CONFLICT` است. شمارهٔ سفارش در MySQL تولید می‌شود و status اولیه `PENDING_PAYMENT` است.

شناسه و fingerprint درخواست نامشخص در sessionStorage نگهداری می‌شوند، بدون توکن. پس از قطع پاسخ، retry همان شناسه را استفاده می‌کند. هنگام reload، `orderByRequestId` فقط برای مالک وضعیت ثبت را بررسی می‌کند؛ اگر سفارش ثبت شده باشد، رسید بازیابی و اقلام سفارش از سبد کم می‌شوند. سبد بعد از پاسخ تأییدشده پاک می‌شود؛ اقلام تازه‌ای که در حین درخواست اضافه شده‌اند حفظ می‌شوند. دادهٔ ذخیره‌شدهٔ مرورگر برای مالکیت، مبلغ یا اعتبار سفارش قابل اعتماد نیست.

## اجرا و بررسی

```sh
nvm use
npm run db:generate
npm run db:migrate
# فقط دیتابیس توسعه
npm run db:seed
npm run codegen
npm run lint
npm run typecheck
npm test
npm run build
npm run format:check
# دیتابیس آزمایشی migrated/seeded و Chrome لازم است
DATABASE_URL='mysql://USER:PASSWORD@HOST:PORT/TEST_DATABASE' npm run verify:checkout
DATABASE_URL='mysql://USER:PASSWORD@HOST:PORT/TEST_DATABASE' npm run verify:checkout-ui
```

Seed توسعه، شناسه‌های شش محصول مرجع فروشگاه را نیز ایجاد می‌کند تا سبد mock با سفارش واقعی دیتابیس قابل آزمایش باشد. این داده‌ها نمونه‌اند؛ production از کاتالوگ API استفاده می‌کند. دادهٔ موقت آزمون‌ها با شماره/شناسهٔ اختصاصی ساخته و پاک می‌شود و دادهٔ موجود دیگر کاربران حذف نمی‌شود.

۷۳ تست واحد، lint، typecheck و build بررسی شده‌اند. آزمون API شامل مالکیت نشانی/رسید، پیش‌فرض، ارقام فارسی، مبلغ سرور، تخفیف، تغییر قیمت، idempotency هم‌زمان، snapshot، محدودیت حذف و محصول ناموجود است. آزمون Chrome شامل ورود و بازگشت از سبد، ایجاد/ویرایش نشانی، کلیک/drag نقشه، geolocation مجاز/ردشده، پیشنهاد نشانی، تخفیف نامعتبر و حذف آن، خلاصه، reload، قطع پاسخ و بازیابی سفارش، سبد و وضعیت پرداخت است. عرض‌های ۳۲۰، ۳۹۰، ۷۶۸ و ۱۴۴۰ و تصاویر `/tmp/behjati-phase6-*` بازبینی می‌شوند. آزمون‌های Homepage، Commerce و احراز هویت نیز برای حفظ رفتار قبلی اجرا می‌شوند.
