# انتشار واقعی سنتی بهجتی

پروفایل انتشار، پیامک واقعی پنج‌رقمی را فعال و ورود با کد ثابت را خاموش می‌کند. درگاه سامان، مشتری‌ها، سفارش‌ها، قیمت‌ها، تصاویر و کلیدهای موجود حفظ می‌شوند.

## روش فعلی کنسول OTP

طبق نمونهٔ جدید مالک از کنسول، درخواست به `/api/send/otp/{apiKey}` فقط `{ "to": "شمارهٔ واردشدهٔ مشتری" }` است؛ شمارهٔ نمونه در کد ثابت نمی‌شود. پاسخ موفق شامل `code` است. همان کد پنج‌رقمی، با حفظ صفر ابتدایی، فقط به‌صورت هش در چالش ورود ثبت می‌شود؛ کد به مرورگر، log یا Git نمی‌رود. سایت کد محلیِ استفاده‌نشده را برای ورود نمی‌پذیرد.

در کنسول، بخش تنظیمات رمز یکبار مصرف را فعال و **طول رمز را ۵** تنظیم کنید؛ متن/عنوان و نوع خط نیز در همان تنظیمات انتخاب و تأیید می‌شوند. این مسیر پارامتر `bodyId` ندارد. شناسهٔ `559650` مربوط به روش جداگانهٔ `shared` با `{ to, bodyId, args: [code] }` است؛ برای ارسال مستقیم همان الگو از `--sms-mode=shared --body-id=559650` استفاده شود. انتخاب روش دیگر به‌خودی‌خود اعتبار کلید را اصلاح نمی‌کند: مقدار کلید باید دقیقاً کلید فعالِ انتهای URL نمونهٔ کنسول باشد.

قرارداد از نمونهٔ مالک و کد عمومی [کنسول OTP](https://console.melipayamak.com/send/otp) و [کنسول shared](https://console.melipayamak.com/send/shared) بررسی شده است. SOAP/REST قدیمیِ مبتنی بر نام کاربری، قرارداد متفاوتی دارد.

## الگوی تأییدشده

شناسهٔ عددی اعلام‌شده توسط مالک برای روش `shared`: `559650`. متن تأییدشدهٔ آن الگو:

```text
وبسایت سنتی بهجتی اردکان
کد ورود به سامانه: {0}
sonatibehjati.ir
لغو۱۱
```

در روش `shared` فقط یک آرگومان، کد تصادفی پنج‌رقمی سایت، برای `{0}` ارسال می‌شود؛ متن کامل از همین شناسه خوانده می‌شود. در روش `otp` متن و طول کد از تنظیمات OTP کنسول می‌آیند. پذیرش درخواست با تحویل روی تلفن متفاوت است؛ دریافت واقعی باید با ورود مالک روی سایت منتشرشده بررسی شود.

## اجرا روی سرور

```bash
sudo -iu sonatibehjati
cd /var/www/sonatibehjati
git switch dev
git pull --ff-only origin dev
npm run production:configure -- --sms-mode=otp --terminal-id=15855486 && bash deploy/update-production.sh
```

کلید API کنسول باید در `MELI_PAYAMAK_API_KEY` فایل خصوصی `apps/api/.env` سرور موجود باشد. کلید در Git یا فرمان عمومی قرار نمی‌گیرد. اگر فقط در فایل محلی توسعه موجود است، همان مقدار باید خصوصی به فایل سرور منتقل شود. فرمان در نبود کلید یا شناسهٔ معتبر یا وجود تعارض مهم، پیش از تغییر تنظیمات متوقف می‌شود.

فرمان، API را production با `SMS_PROVIDER=melipayamak` و مسیر `otp` تنظیم می‌کند، `CHECKOUT_PAYMENT_TEST_ENABLED` و `ADMIN_PAYMENT_TEST_ENABLED` را خاموش و `DEV_OTP_CODE` و نشانی بانک شبیه‌ساز را خالی می‌کند. خرید واقعی با `sep` و ترمینال صادرشده فعال می‌ماند. فروشگاه از API داخلی 4100 استفاده می‌کند و `SEO_INDEXING_ENABLED=true` می‌شود.

در فایل‌های دارای اولویت بالاتر `.env.local` و `.env.production.local`، فقط پرچم‌های قدیمی تست/SEO هماهنگ می‌شوند؛ سایر تعارض‌ها پیش از هر نوشتن گزارش می‌شوند. تنظیمات نامرتبط، توکن‌های تأیید مالکیت و کلیدهای احراز هویت حفظ می‌شوند. فایل‌های تنظیمات خصوصی با دسترسی 600 ذخیره می‌شوند.

کانفیگ `payment-live.conf` نصب‌شده برای پرداخت موفق فعلی مناسب است؛ تغییر دوبارهٔ Nginx لازم نیست. این قابلیت migration جدید یا seed ندارد. اسکریپت معمول استقرار، بیلد و restart را انجام می‌دهد.

## رفتار انتقال

- توکن‌های access و refresh دورهٔ تست که اثبات ورود پیامکی ندارند، در production واقعی پذیرفته نمی‌شوند؛ مشتری قبلی یک بار با پیامک وارد می‌شود. داده‌ها و نشست مدیرها حذف یا تغییر نمی‌کنند و ورودهای واقعی بعدی با restart معمول حفظ می‌شوند.
- درخواست شش‌رقمی قدیمی در sessionStorage مرورگر کنار گذاشته می‌شود؛ راهنمای کد ثابت نمایش داده نمی‌شود. ارسال مجدد، محدودیت تلاش، انقضا، مصرف یک‌باره و عدم ثبت کد در log حفظ می‌شوند.
- منو و صفحهٔ آزمون درگاه مدیریت در حالت غیرفعال پنهان‌اند؛ سوابق بانکی حذف نمی‌شوند و رسیدگی به تراکنش‌های قبلی ادامه دارد.
- لینک اجتماعی بدون نشانی حذف شده و اینستاگرام رسمی فعال است. فقط متن موقتِ دقیقِ واردشده از کاتالوگ قدیمی، هنگام نمایش با نام/وزن ثبت‌شده جایگزین می‌شود؛ توضیحات اختصاصی مدیر، قیمت‌ها و دادهٔ ذخیره‌شده دست‌نخورده‌اند.

## بررسی بعد از استقرار

۱. `/login` را در مرورگر ناشناس باز کنید؛ پیام ورود آزمایشی یا کد ثابت نباید دیده شود.

۲. با شمارهٔ متعلق به خودتان دریافت پیام مطابق تنظیمات روش انتخاب‌شده و ورود با کد پنج‌رقمی را بررسی کنید. حساب و سفارش‌های قبلی باید حفظ شده باشند. سپس خروج، ورود مجدد و ارسال دوباره پس از شمارنده بررسی شوند.

۳. اگر پیامک نمی‌رسد، اعتبار پنل، فعال بودن الگو برای همین API key و پاسخ سرویس بررسی شود؛ کد ثابت دوباره فعال نشود.

پس از یک بار تلاش برای ورود، علت قابل‌بررسی را از لاگ API بگیرید:

```bash
pm2 logs sonatibehjati-api --err --lines 80 --nostream
```

رکورد `[SMS delivery failed]` شامل دستهٔ خطا (`reason`)، وضعیت HTTP، کد منفی پاسخ در صورت وجود، متن وضعیت پالایش‌شدهٔ سرویس و شناسهٔ الگو است. `provider_rejected` یعنی پاسخ موفق HTTP، شناسهٔ ارسال معتبر ندارد؛ متن وضعیت برای بررسی کلید/الگو/اعتبار استفاده شود. `http_error` یعنی پاسخ غیرموفق HTTP؛ `invalid_response` یعنی پاسخ JSON قابل‌خواندن نیست؛ `network_error` و `timeout` مربوط به ارتباط‌اند و کدهایی مانند `ENOTFOUND` در صورت وجود ثبت می‌شوند. `invalid_otp` همراه `otpCodeLength` یعنی طول کد برگشتی با ۵ رقم مورد انتظار سایت هماهنگ نیست؛ طول را در کنسول اصلاح کنید. در روش OTP به‌جای bodyId، `mode: otp` ثبت می‌شود. هیچ نتیجه‌ای دربارهٔ علت سرور بدون همین خروجی قطعی نیست. شماره، کد ورود، کلید، URL خصوصی و پاسخ خام ثبت نمی‌شوند و متن عمومی سایت همچنان کلی می‌ماند. صرفاً اجرای فرمان لاگ هیچ پیامکی ارسال نمی‌کند.

۴. خرید عادی و نتیجهٔ پرداخت سامان بررسی شوند. پرداخت واقعی پول جابه‌جا می‌کند؛ در آزمون‌های خودکار از بانک شبیه‌ساز استفاده می‌شود. کاربر قبلاً درگاه واقعی را تأیید کرده است.

۵. robots باید دسترسی عمومی و آدرس sitemap را نشان دهد؛ sitemap شامل محصولات فعال باشد. تأیید مالکیت Search Console/Bing مستقل از پیامک است.

## بررسی توسعه

```bash
npm run lint
npm run typecheck
npm test
npm run build
npm run verify:production-release
```

`verify:production-release` روی fixture موقت و با درخواست پیامک mock اجرا می‌شود؛ هیچ پیامک، درخواست بانک یا اتصال دیتابیس واقعی انجام نمی‌دهد. محیط توسعهٔ محلی همچنان توسعه می‌ماند؛ فرمان `production:configure` مخصوص سرور انتشار است.
